This spec defines how the seller reaches the CMO **only through the CEO**: how the CEO delegates, how it collects what the CMO is missing, how an image reaches the CMO, how the metered generation is approved **inside the chat**, how the result is presented, and what the CMO dashboard becomes (a read-only showcase). It adds **no new CMO capability** (`slim-cmo-agent.md` C3 stands) and **no new model authority**: the classifier still only selects from the closed catalog; every question, plan line, label and figure is written by code; no LLM originates or alters a number, a plan or an approval.

## 4. Goals and non-goals

**Goals.** One front door for AI work. A missing input is asked once, in the conversation, by code, and remembered. An image reaches the CMO only by reference, only to an operator-controlled endpoint, and only after the seller has seen where it goes. A quota-consuming run happens only after the seller approves the exact frozen plan **in the chat**. The result is shown verbatim with provenance. The CMO page becomes a faithful, honest, searchable library of what was actually produced.

**Non-goals.** Any new CMO capability or output type; a marketplace write; CEO-authored copy; redesign of PI, CI or CFO surfaces (CD3 future direction only); changing the sidebar/logo; changing entitlement caps or units; typed-text approval (C3); automatic retry; multi-image analysis; image retention policy (slim-cmo Q6); a hosted/third-party vision endpoint.

## 6. Core rules

### 6.1 CEO-first principle and its boundary (CD1, CD3)
1. After this spec is implemented, **no seller-facing screen starts a CMO generation, analysis, approval-of-copy or trend run except through a CEO turn.** The CMO frontend contains no control that calls a CMO `POST` route (§6.8).
2. The CEO is the only caller of the CMO from the seller's side; the CMO still never calls another agent, and the CEO still routes through the single dispatch choke point (permission, attachment, entitlement, quota, `agent_run`, provenance) for every CMO leg exactly as for any other agent.
3. **Stays where it is** (CD3): account/settings (Clerk, billing), data-management (report upload on Finance, tracked competitors, cost entry), the CEO Hub itself, and the read-only agent dashboards. PI, CI and CFO dashboards keep their current forms **until the owner commissions the same treatment**; this spec lists no work for them.
4. Future direction (not scheduled): the same delegation contract (§6.2), requirement declaration (§6.3), reference hand-off (§6.5) and in-chat approval (§6.6) are intended to be reused per agent. A new agent adopting it needs its own spec amendment; this spec does not pre-approve it.

### 6.2 The delegation contract (CEO → CMO)
1. **One CMO action per turn** (C4 holds): the classifier selects exactly one registered key from the closed catalog. Chat may reach: `cmo.generate_title_sets`, `cmo.generate_listing_copy`, `cmo.generate_description`, `cmo.generate_bullets`, `cmo.generate_keywords`, `cmo.generate_backend_terms`, `cmo.generate_hashtags`, `cmo.catalog_answer`, `cmo.market_trends` (via preview), plus the zero-unit record/read actions in A9 and the DD2 hand-off action. Which of these are enabled in chat is gated by the approval build (A1): until it ships they stay refused (D-8).
2. **The CEO builds the CMO request only from validated inputs**, never from model output: (a) values parsed by code from the seller's own answers (`input_session` parsers); (b) the classifier's slot **text**, which is re-validated by the same parsers before use; (c) stored, tenant-scoped records selected by id (an `image_analysis_id`, an approval id, a confirmed niche-term id); (d) an `attachment_id` (§6.5). Free text from a model, from specialist output, from an attachment's extracted text, or from an image's visible text **never** becomes a slot (R9 stands).
3. **CMO-side validation runs before a plan exists**: the CEO calls the CMO's own request validation (declared fields only, text length caps, the forbidden-content scan) on the assembled inputs; a failure yields a **re-ask for that field with the reason**, never a plan and never a silent edit.
4. A delegation that is not yet complete ends the turn `CLARIFIED` (no CEO unit, `ceo-agent-orchestration.md` §6.42); nothing runs, nothing is metered, nothing is sent.
5. When all requirements are met and the action is approval-required (`ceo/approval_gate.py`; metered or `SELLER_DATA_OUT`), the turn ends `PLANNED` with a plan (§6.6). Otherwise it runs as today.

### 6.3 What the CMO may ask for, and how the CEO asks (CD1)
**Closed requirement vocabulary** (declared by the CMO; extended only by a spec edit plus a code table change, never at runtime):

| Code | Meaning | Required when | Notes |
|---|---|---|---|
| `MARKETPLACES` | one or more of Amazon / Flipkart / Meesho | every title/copy/hashtag/standalone/backend-term action | CEO never defaults it (`slim-cmo-agent.md` §6.1, orchestration §6.9). Backend terms: Amazon only. |
| `PRODUCT_NAME` | the product as the seller lists it | title and grounded-copy actions | Never taken from an image. |
| `GROUNDING_TITLE` | an approved title record or a seller-supplied title | copy, description, bullets, keywords, backend terms | Option ids come only from the seller's click/message; the CEO never chooses (C8). |

| `PRODUCT_FACT(attribute)` | one named attribute from a **closed list** (brand, colour, material, size, product type, category hint) | optional, asked only when the action's fact basis needs it | Seller-typed value → `SELLER_PROVIDED`. |
| `IMAGE` | an offer to attach a product photo | **never mandatory**: always has "Skip"; the text workflow works without it (`slim-cmo-agent.md` §6.2.1) | Asked when the seller refers to their photo, or as an optional offer. |
| `IMAGE_HINT_CONFIRMATION(attribute)` | confirm / correct / skip one `UNVERIFIED_HINT` | only after an analysis exists and only for attributes the action would use | Maps to `cmo.confirm_image_hint` (zero-unit). |
| `NICHE_CONFIRMATION` | confirm / edit / reject suggested niche terms | `cmo.market_trends` only | Supersedes "stays on the CMO page" (orchestration §6.40); decided, CD12. The CMO dashboard has no niche input. |
| `MARKET_TRENDS_PREVIEW_ACK` | the exact outbound queries shown; part of the plan, not a separate confirm | `cmo.market_trends` | Preview digest frozen in the plan. |

Rules:
1. The requirement list is the output of a **pure function** over the inputs so far (DD1). Same inputs → same list, in a fixed order. A requirement the seller already satisfied is never asked again within the delegation (§6.4).
2. The CEO asks **one question per turn**, wording written by code, at most **three real options plus "Other, type it" and Cancel** (orchestration §6.34), the first option recommended by a stated code rule. Every reply is parsed by code against the one field being asked; an unparseable reply repeats the same question with the reason; a free-form reply is never given to a model to extract a value.
3. **Bounded (CD13).** Three server-side limits, read from configuration at use (never from the client, the model or the request):

| Variable | Default (owner) | Meaning |
|---|---|---|
| `CMO_DELEGATION_MAX_QUESTIONS` | `8` | Maximum clarification questions the CEO asks for one task. Every CEO clarification message counts, **including re-asks**. Questions 1-8 are asked; a 9th is never asked. |
| `CMO_DELEGATION_MAX_REASKS` | `2` | Maximum re-asks of the **same** missing field after an unparseable/invalid reply: a field is asked at most 1 + 2 = 3 times; the 3rd failed answer reaches the limit. |
| `CMO_DELEGATION_IDLE_EXPIRY_SECONDS` | `86400` (24 h) | A pending task expires when `now - last_activity_at >= value`. Activity = a seller reply or a CEO question on that task. Compared with the server clock only. |

A value that is missing falls back to the default; a value that is present but not a positive integer is a configuration error and **fails closed** (`CONFIG_INVALID`: the CEO declines to start a CMO delegation with a plain message; nothing is guessed). Lowering a value never retroactively corrupts an open task: it is evaluated at the next question/reply. **Boundary behaviour:** 8th question is asked, the 9th is blocked; the 2nd re-ask is asked, a 3rd is blocked; at 86399 s idle the task is live, at 86400 s it is expired.
   - **Question or re-ask limit reached:** the turn ends `CLARIFIED`; the CEO states, in code-written text, which limit was reached, what is still missing and which inputs were collected, runs nothing, meters nothing, and offers **Restart** (a choice chip). Restart opens a fresh delegation with counters at zero; previously collected inputs are offered back for re-confirmation, never silently reused.
   - **Idle expiry:** the collected inputs and attachment references are **preserved** (they stay on the stored question message, DD5/§5.3) but the task is marked `EXPIRED`. When the seller returns, the CEO restates the collected inputs and requires a **fresh confirmation** (Confirm / Change / Restart) before a plan is built; execution is impossible without it, and a plan's own approval (30 minutes, C6) is a separate, later step. An attachment reference is re-validated at that point. Nothing ran, was metered or was sent while expired.
4. Cancel at any time; cancel discards unconfirmed delegation state and runs nothing. Facts already recorded as `SELLER_PROVIDED` records (for example by `cmo.confirm_image_hint`) are append-only and stay.
5. Answers are accepted only from the **requester** who started the delegation (same user); another member's reply is an ordinary message.
6. A seller who has not attached the CMO, or lacks `agent.cmo`, is refused **before** any question is asked (orchestration §6.35); a missing `research.market_trends` key refuses the trend flow before the preview.

### 6.4 Confirmed-fact preservation and attribute basis (CD2)
1. Every value the seller gives or confirms is stored in the delegation state (§5.3) with its basis and is **frozen into the plan's slots** (`ceo-approval-workflow.md` §5.3). When the CMO generates, it writes `seller_fact` rows as it does today (`slim-cmo-agent.md` §6.1, append-only). Nothing the seller confirmed is asked for again in the same delegation, in a follow-up turn of the same product ("this product" resolves by code, `agent-needs…` §5.7), or after a plan is declined and re-requested within the delegation's lifetime.
2. A **changed** answer supersedes the earlier one in the state (the change is recorded with time and actor); because the plan's slots are part of the hash, a change after a plan exists is a **material change**: a new plan, a new hash, the old plan `SUPERSEDED` (`ceo-approval-workflow.md` §6.2).
3. **No attribute is ever guessed from an unverified image.** Attribute basis follows `slim-cmo-agent.md` C9/§6.2.1: while the vision gate is closed (launch state) every image-derived value is an `UNVERIFIED_HINT`; it is shown to the seller only as **"from your attachment — suggested, not verified; please confirm"**; it is never a claim in generated copy, a title, a catalog answer, or a context passed to GST/CI/trends; only a seller's confirmation (a new `SELLER_PROVIDED` fact) makes the *seller's* statement usable, and it does **not** make the image or the provider trusted.
4. **Observation vs inference are separated in what the seller sees.** The CEO renders two blocks, both by code: **"Read from your attachment"** (only the closed-schema fields `color`, `material`, `size`, `brand`, `product_type`, `visible_text`, each literally observed or `UNKNOWN`, digits and policy-flagged values already discarded by the CMO parser) and, if shown at all, **"Not from your attachment"** (anything else the CEO said). An inference such as "this looks like a premium watch" is never placed in the first block, never worded as an observation, and the CEO composer is never given the image (text-only, orchestration §6.9).
5. Text visible inside an image or attachment (`visible_text`, extracted text) is **untrusted quoted data**: it cannot create a requirement, answer a question, set a slot, approve anything or instruct the CEO or CMO (R9, orchestration §6.34).
6. A numeral read from an image never reaches copy or an answer as fact (CI Q18, `slim-cmo-agent.md` §6.2 hazard).

### 6.5 Attachment hand-off, by reference (CD5)
**Flow.** The seller attaches a file to a CEO message (existing upload, `files.upload`/`agent.ceo`-gated, limits and type detection as built). The CEO then decides, by code, whether a registered agent action accepts it and what to hand over.

1. **The CEO passes a reference, never bytes.** The hand-off value is `{attachment_id}`. The CEO first validates it with `investigation_repo.get_attachments(tenant, investigation, [id])` (so a foreign or other-investigation id is simply "not found", indistinguishable from a missing one), checks `detected_type` against the target action's accepted types (below), and that `extraction_status` is not `FAILED` where the action needs a read. No attachment bytes, thumbnail, base64, extracted text or hash of content ever enters an LLM prompt, an `investigation_message`, the rolling summary or a finding.
2. **The agent loads through its own tenant-scoped read.** The handler re-validates `attachment_id` against `(tenant_id, investigation_id)` under RLS (it does not trust the CEO's check), reads the bytes itself, and processes them with its own pipeline. A bound `sha256` in the request must equal the stored one (defence against a changed row; the table is append-only, so a mismatch means a bug and fails closed).
3. **Accepted types per agent** (a closed table in code, checked at the hand-off and again in the agent):

| Agent | Accepted | Receiving path | Status |
|---|---|---|---|
| CMO | PNG, JPEG, WEBP (product photo) | DD2 action → existing `cmo_images` normalise/store/analyse → `VisionProvider` (`CMO_VISION_OLLAMA_HOST`) | specified here |
| CFO | CSV, XLSX | existing deterministic table reading (`attachment_tables.py`); persistent import stays on Finance upload (orchestration §6.34 as-built (3), §6.43) | unchanged; recorded for completeness |
| CI | PNG, JPEG, WEBP (competitor screenshot) | CI evidence path; vision endpoint rules identical | later adapter, **not specified here** |
| PI | PNG, JPEG, WEBP (reference image) | PI adapter | later adapter, **not specified here** |

4. **Only an operator-controlled endpoint may receive an image.** The target endpoint is resolved through `config.verified_llm_endpoint`; if it is not in `LLM_OPERATOR_CONTROLLED_HOSTS` the hand-off **fails closed before any bytes are read** (`LlmEndpointNotVerified` → the seller is told the vision service is not available; nothing sent). The plan builder resolves the same endpoint at planning time and refuses to build a plan whose endpoint is not verified (the plan lists the integration `UNAVAILABLE`, approval then refused with `INTEGRATION_UNAVAILABLE`, `ceo-approval-workflow.md` E12). The endpoint is re-resolved at approval time (C9).
5. **The plan shows the hand-off** (DD3/DD4). For a plan whose legs consume an attachment, the card contains, written by code: the file name (escaped), its detected type, the first 8 characters of its `sha256`, the sentence "This image will be sent to *<endpoint label>* (operator-controlled) to read what is visible; nothing is sent anywhere else", the model label (`CMO_VISION_MODEL`), the trust-gate state ("observations will be unverified suggestions until you confirm them" while the gate is closed), the unit cost ("0 CMO units; the generation that follows is a separate approval"), and whether the file's EXIF/location data is removed before analysis ("removed before the model sees it", true for the CMO path). `data_basis` carries `{kind: "ATTACHMENT", id, as_of, fingerprint = sha256}`.
6. **One file → one purpose.** An attachment is handed to the action the plan names; it is not forwarded to a second agent unless a second plan says so.
7. **Shared-store caveat (A4).** The raw original (with EXIF/GPS) remains in `investigation_attachment`; only the CMO copy is re-encoded. Retention, deletion and EXIF handling for the shared store are an open policy (OQ-8, relates to slim-cmo Q6, orchestration Q34, `rag-knowledge.md` if it ever reads this table).

### 6.6 Approval inside the CEO chat (CD4)
**Build order is fixed by the owner: the approval workflow first** (§10). This section specifies only what the existing workflow gains for the chat; it does **not** weaken any of its rules.

1. **Which CMO actions require a plan:** exactly those `approval_gate.plan_required` already flags: every metered `cmo.generate_*` and `cmo.catalog_answer`, and `cmo.market_trends` (metered and `SELLER_DATA_OUT`). Zero-unit actions (`cmo.approve_title`, `cmo.confirm_*`, `cmo.suggest_niche_terms`, `cmo.market_trends_preview`) never need a plan. The DD3 image-analysis action **always needs its own small plan card** (option A, CD10): "send this image to <endpoint label>, 0 CMO units". Its approval and the generation plan's approval are separate clicks. Metering rule: the analysis plan consumes no CMO units; the later generation plan is never charged for the analysis again; a failed or refused analysis consumes nothing; re-approving or replaying an already executed plan returns the stored result and records no second meter event. Whether the analysis plan's execution turn consumes a CEO conversation unit is OQ-18 (open; blocks the attachment hand-off checkpoint).
2. **The plan card is a chat message** (`PLAN` kind) in the CEO thread, rendered from the stored plan row by the frontend (never parsed from text): what will run (agent, action, marketplaces, product), the **exact frozen inputs** the seller gave or confirmed, **units** (CMO units; trend runs also the shared meter), **what leaves Metrion and to where** (trend queries listed, up to the preview's limit), the attachment hand-off line (§6.5-5), assumptions, the seller's remaining cap where known, the expiry countdown from the server `expires_at`, and the plan hash.
3. **Approve and Decline are buttons on that card**, shown **only** when the plan is `AWAITING_APPROVAL` **and** the viewer is the requester (AC-A17). They call `POST …/plans/{id}/approve` (with the card's `plan_hash`) and `…/decline`. The CMO dashboard has no approval control.
4. **A typed "yes", "go ahead", "run it" is not approval** (C3, `ceo-approval-workflow.md` §6.4; **decided, CD11**). Only an explicit click on the correct confirmation card, an API call bound to the plan id **and** `plan_hash`, can approve quota-consuming work. A typed message after a card is an ordinary message; the CEO may remind the seller that the card must be used. The classifier has no "approve" intent and no slot that can carry a plan id.
5. **Two different "approvals" are never conflated.** Choosing a title (`cmo.approve_title`, a seller's selection record, free) happens by an option card in chat. Approving a **plan** (quota consumption, `investigation_plan`) happens on the plan card. A copy-pack request after a title choice is a **new** plan with its own approval, because the pack depends on the chosen title (generation legs cannot consume another leg's output in one turn, AC4). The seller therefore sees one plan card for titles and a second for the pack per marketplace set; this cost is stated in the first card ("copy pack is a separate approval").
6. **Execution turn.** Approval creates the execution turn (`route_source='APPROVAL'`), runs exactly the frozen legs, and the result is posted to the same conversation (§6.7). `PLANNED`, declined and expired turns cost no CEO unit; the execution turn is metered once when `DUE` (`ceo-agent-orchestration.md` §6.42). Quota, permission, entitlement and attachment checks are re-run at approval and again inside the CMO leg (`ceo-approval-workflow.md` §6.6).
7. **Declined / expired / superseded / stale / outcome-uncertain** plans are shown on the card in their final state, and the CEO says plainly what happened and that nothing ran (or, for `OUTCOME_UNKNOWN`, that the request may already have been sent and will not be repeated automatically). The seller asks again for a new plan.

8. **Compact presentation (amendment 2026-10-13, from the owner's first live chat).** The stored plan, its hash and its disclosure wording are unchanged and complete; only the chat presentation is shorter. The plan carries a code-written `title` and 3-5 `compact_lines` (what runs, the confirmed inputs, the model, the cost in one line, the validity). The card shows those lines and the Approve / Decline buttons; the complete text, the frozen inputs, the disclosure wording and the full hash are behind a collapsed **Details** toggle. The CEO's chat message is one short line that states once that nothing runs until Approve is pressed and that typing yes does not approve. After a decision the card shrinks to its title and the conversation gets one line (`You approved: <plan title>`), never the plan text again.
9. **Optional high-value details (same amendment).** Before a titles plan the CEO asks, one question at a time and each skippable, for brand, size or capacity, 1-3 key features, main use or target buyer, and 1-3 search words; bullets, description, keywords and listing copy ask for brand, size and features after the seller's title. They count inside the question limit (§6.3) but never stop a task at it: when only skippable details remain at the limit the task goes on without them. Details the seller already confirmed for the same product earlier in the conversation are carried from the earlier plans and not asked again. When fewer than two details beyond the product name are known, the plan card and the result say "Thin input - add brand/size/features for stronger titles."
10. **A length rule that is not sourced is said to be so.** A result fitted to a `TEST_FIXTURE` row is labelled "placeholder limits for testing, NOT a verified marketplace rule". Verified rows are loaded only by the operator tool `packages/slim-cmo/scripts/seed_format_constraints.py` from a reviewed JSON that carries each rule's source page and check date (§13 OQ-20).

### 6.7 Result presentation
1. **Artefacts are shown verbatim**, quoted and labelled ("Written by the specialist from the details you gave. Read it before you use it; Metrion has not checked it against your marketplace account."), exactly as orchestration §6.35 (R9 amendment): no composer call, no rewording, merging or re-ranking, no numeric gate by a second model. Character and byte counts are computed by code against the stored `format_constraint` and shown with the limit and the rule's `source_url` and `verified_at`.
2. **Attribute-basis labels travel with the text** (`SELLER_PROVIDED | IMAGE_OBSERVED | ESTIMATED | SOURCE_DERIVED | UNKNOWN`); an image-derived attribute that the seller has not confirmed is never stated as fact and is labelled "from your attachment".
3. **Trend reports** keep all seven sections, source links, publication and retrieval dates, corroboration labels and the evidence-and-limitations section; the "CMO's interpretation — not a verified market fact" label stays; "attracting attention" is never converted to "trending" or "in demand"; nothing is shown that the report does not contain (a source with no stated publication date shows "publication date not stated", never a guessed date).
4. A failed artefact is a named gap with the missing detail, never a result; a `PARTIAL` multi-marketplace request states which marketplaces were delivered and which failed and what each cost.
5. The finding written for the shared-findings tier remains `CONTENT_READY` with the written content **not** copied into it.
6. After a successful result the CEO offers, as option chips, the next legitimate steps (choose a title, request the copy pack, view it in the CMO page) — choices, never auto-actions.

Light and dark themes and keyboard operation are required; visual design is not final (`design_status.md`) — structure and data rules here are what is binding, not the mockup's styling. **Owner direction (2026-10-12, final):** follow the reference (`Slim-CMO-Dashboard.svg`, `docs/design/references/2026-10-11/`) closely in layout and hierarchy, rendered in Metrion's black / green / white theme (theme values stay configurable, never coupled to logic); real saved data only; search, filters, copy and a result detail view; **no generation forms or input fields** other than the search box and filters.

### 6.10 "Frequently used": what is recorded and what feeds it (CD7, CD14)
**Finding (A7): usage tracking did not exist before this spec.** Until the §5.1 table is migrated and events exist, the Frequently-used view **shows "Frequently used unavailable"** (reason: "usage is not recorded yet") and Recent is the working default. Nothing popularity-like may be derived from guesses, rank, recency, character count, requests or a model.

**Distinct events (CD14).** `GENERATED` (server), `VIEWED`, `COPIED`, `MARKED_USED` (§5.1). Each is stored and displayed as its own count. **Generating or approving content is not "used on a marketplace":** `GENERATED` is not use, and a `cmo_title_approval` row is a seller's *selection* record, not use.

**What feeds "Frequently used" (specified by this spec at the owner's request; recommendation adopted):** **only `COPIED` and `MARKED_USED`.** `GENERATED` and `VIEWED` are shown on the item as separate, labelled counts ("generated 2 times", "viewed 5 times") and never ranked as use. "Requested N times" (from `cmo_generation`) and "approved" (from `cmo_title_approval`) may be shown as their own labelled facts, never under the "Frequently used" heading and never summed with the use events.
**Ranking rule:** rank by the count of `COPIED` + `MARKED_USED` events for the same normalised text and `(product, marketplace)`, **de-duplicated per the OQ-19 window**; ties broken by most recent such event; each item shows its count with the breakdown ("copied 3 times, marked used 1 time") and "recorded since <first event date>". An item with zero such events is not in the Frequently-used view. If a minimum count or look-back window is configured (names in OQ-19; unset ⇒ no minimum and all-time, stated on the page) it is applied server-side. With no copy/mark-used events at all: "Frequently used unavailable".
Every item keeps its product/SKU, marketplace, generation date and source references (CD6).

### 6.11 Direct CMO routes: audit and safe deprecation (CD15)
**Rule.** `backend/src/backend/api/v1/cmo.py` stays. Its handlers are the single implementation the CEO's CMO actions run (`agents/ceo_hub_cmo.py` calls "the very same handler code" with the permission set per action), so removing a handler would remove a CEO capability. The routes are therefore **internal authorized capabilities**: still `require_auth` with `agent.cmo` (+ the per-route permission), still metered and tenant-scoped, no behaviour change.
**Deprecation, in order (none is a deletion):**
1. The seller-facing frontend stops calling every `POST` below (AC-D1). `frontend/components/cmo/*` generation components are removed or replaced by the showcase.
2. Each deprecated route is marked in the OpenAPI document (`deprecated=True`) with a description pointing to the CEO flow, and responds with a `Deprecation` header. Behaviour is unchanged.
3. A **server-side switch** `CMO_DIRECT_ROUTES_ENABLED` (default `true`; the implementer may set it `false` per environment) gates the seller-facing generation `POST`s. When `false` they return `410 Gone` with a stable error code (`USE_CEO_CHAT`), **without** affecting the CEO path, which calls the handlers in-process. The default flips to `false` only after the removal gates below pass; flipping the default is a later, recorded owner decision.
4. Removal gates (all must hold before any route is deleted): zero seller-facing frontend callers (test enumerates network calls); every dependent test below has been migrated to the CEO path or the in-process handler; the CEO path covers each capability; a release has run with the switch `false` without a `USE_CEO_CHAT` hit in logs.

**Routes** (all under `/api/v1/cmo`; verified in `api/v1/cmo.py` on 2026-10-12):

| Route | Class | Disposition |
|---|---|---|
| `POST /title-sets`, `/listing-copy`, `/description`, `/bullets`, `/keywords`, `/backend-terms`, `/hashtags`, `/catalog-answers` | metered generation | Deprecated; gated by `CMO_DIRECT_ROUTES_ENABLED`; CEO reaches the same handlers after plan approval |

### 6.12 CMO 3.0 M0 — the chat steps that close the seller loop (amendment, 2026-10-30)

**Status of this section: implemented** (branch `feat/cmo-3-m0`; tests in `backend/tests/unit/test_cmo_m0_unit.py`, `backend/tests/integration/test_cmo_m0_integration.py`, `backend/tests/integration/test_ceo_cmo_m0_chat.py`). The rest of this document's "nothing is implemented" status line is stale: the delegation loop, plan cards, photo hand-off, showcase and CI-informed writing exist in code. Behaviour below is authoritative; where it differs from an earlier section, this section wins.

**M0-1 Product identity.** A product the seller names in chat gets a deterministic `sku` = the name lower-cased and reduced to letters, digits and hyphens (max 120; `cmo_chat.product_sku`). The same name always gives the same `sku`; a name too short to identify anything gives none. Every CMO writing action (not market trends) carries it, so what the seller confirmed is saved in `seller_fact` against the product, loads again in the next conversation (`load_facts` is by exact non-null `sku`), and the product appears on the dashboard under its name. A loosely named product ("my AquaNest bottle") resolves to a saved product only when **exactly one** saved name contains all its informative words; two candidates or none means the seller is asked, nothing is guessed. Saved facts are offered as already-answered questions (so they are not asked twice), listed on the plan card, and the seller's Approve click is their re-confirmation; the CEO says it reused them and the seller may change anything.

**M0-2 Choosing a title in chat (`cmo.approve_title`).** Zero units, no plan card: the seller's own answer is the choice (decision CD4 distinguishes a *choice record* from *plan approval*, and a typed "yes" still approves no plan). A guided session shows the newest saved title set per marketplace (all options, numbered, verbatim) and accepts: a click, a number ("2", "option three"), or the seller's own title typed in full (at least four words, not a question). "yes", "ok" and similar are not titles and are asked again. With titles for more than one marketplace, the marketplace is asked first. A typed title is re-validated against the **current** marketplace rule by the existing approval service (`edited_by_seller = true`); a title that breaks the rule is refused and nothing is saved. The CEO never chooses for the seller. CEO-proposed rewording of a title ("move 1 litre earlier") is **not** part of M0: the seller types the wording they want.
After a choice, the result says it is saved in Metrion, that nothing was published, and offers the next step (listing copy) as a separate plan. A grounded task (description, bullets, keywords, backend terms, listing copy) offers the approved title first; if the title given equals the approved one for that product and marketplace, the plan is grounded on `approval_id` (`APPROVED_TITLE`), otherwise on `seller_title` (`SELLER_SUPPLIED_TITLE`). Exactly one of the two is ever sent (existing rule). The plan card says "Written from the title you approved".

**M0-3 Photo hints confirmed by the seller.** When the seller confirms or corrects a photo-suggested detail with their own answer, the CEO also records it through the same zero-unit action as `cmo.confirm_image_hint` (a new `SELLER_PROVIDED` fact attached to the product and linked to the reading by `image_analysis_id`; the reading is never changed and the photo or model does not become trusted). Best-effort: if it cannot be recorded the plan still carries the answer as the seller's inline statement. A skipped detail is not recorded.

**M0-4 Catalog details (`cmo.catalog_answer`) and property questions.** "What are the colour and material of my bottle?" starts a guided session (product, which details — category, colour, material, size, weight, dimensions, brand — then the optional facts), ends on a **plan card** (1 CMO unit per marketplace answered, 1 when none is named; metered only for a delivered answer), and runs the existing catalog service. No language model is used and the card says so. Each line states how sure it is ("you told me", "seen in your photo", "an estimate, confirm it before you list", "not known yet"); an unknown stays unknown. A yes/no question about a product **property** ("is my bottle dishwasher safe / leakproof / insulated") is answered by code from the seller's own saved facts: if they gave it, it is quoted as their statement (not checked by Metrion); if not, the answer is "not confirmed" and the CEO will not state it in any title, bullet or description until the seller confirms it. No unit is used and no model is called.

**M0-5 History in chat.** "Show my selected title and description" is answered from `BS_CMO_CONTENT_LATEST` (read-only): a block **"Titles you chose"** comes first (marketplace, product, the exact title, the day, whether the seller worded it, and how many times it was copied / marked used), followed by the latest written content. Copied, approved and live on a marketplace are three different things: the block states that copying or marking used only records an action in Metrion and does not prove publication, and "does copying mean it was published?" is answered "No" by code. Metrion never knows a title is live.

**M0-6 Configuration verification.** `packages/slim-cmo/scripts/verify_cmo_readiness.py` is a read-only operator check: per marketplace, is there a `VERIFIED`, sourced, recently checked rule with a counting rule (else generation fails closed `COUNTING_RULE_UNVERIFIED`); which required configuration keys are absent (none is defaulted); whether the photo trust gate is open. Loading reviewed rules stays a human step (`seed_format_constraints.py`).

**Not changed:** typed text never approves a plan; every metered action is still a stored plan with a hash; tenant comes from the session only; nothing is written to a marketplace; the dashboard stays read-only.

### 6.17 CMO 3.0 M7 - listing history, comparison and advice in the chat (amendment, 2026-10-31)

The seller asks about their listing history in plain words and the CEO answers with a `LISTING_HISTORY` card. It is a **direct, free, code-written answer** like M4/M5/M6 reads: no model call, no plan card, no approval step, no unit, and nothing is generated, edited, approved or published. Typed text never approves anything. The CEO chooses *what* to fetch (product, marketplace, versions); the CMO side (`services.cmo_history`, rules in `slim_cmo.history`) performs the exact comparison. It sits after the M6 listing step, so "show my listing" and the edit sentence keep their M6 meaning; a message that is not a history request goes on to the rest of the CEO unchanged.

**Requests recognised (closed set).** Show my listing history · show my latest / previous / original / version N listing (for a product, for a marketplace) · compare my old and new listings / compare version A and version B / compare my previous listing with the latest one · what changed in my latest listing · which keywords were removed / added · why was this listing revised · show me the audit changes · what claims were introduced in the latest revision · which listing version is approved for use · show my Amazon listing changes · what should I improve next. The follow-up forms (keywords, audit, claims, improve) are recognised on their own only straight after a history answer; otherwise they need the word "listing", "version" or "revision".

**Resolution, in this order.** Product: the words the seller used matched against their saved products (exactly one match or a question); else the product of the previous history card in this conversation; else the only product that has listings. Marketplace: named, else the previous card's, else the only one the product has; two or more = one question. Versions: explicit numbers; "previous" = the one before the latest; "latest" = the newest; "original" = version 1; "my previous listing with the latest one" = the last two. Two sentences that leave the pair open ("my old and new listings" with more than two versions, "compare version 2") get **one** short question with the choices as buttons. A product that is not saved, or a version that does not exist, is asked about (with the products or versions that exist), never guessed, and a product with one version or none is told so in plain words.

**Conversation context.** A question is stored as a `CLARIFY` card with the request it belongs to; the seller's next short message ("Amazon", "version 1 and 3", a product name) answers it and the original request continues. The newest history card also supplies the product and marketplace for follow-ups. Every answer is stored in the conversation as the card (data only).

**Answers.** One plain paragraph written by code from the card (what changed, how many keywords were added/removed/moved/kept, the audit change, any new claim your confirmed facts do not support, the suggestions) plus the card. The text says that differences in saved text do not show a version performs better, that approval only records a decision in Metrion, and that Metrion cannot see which version is live. It never reveals internal ids, never claims an effect on sales, ranking or demand, and never calls a version published.

**Layers.** No new registry action, effect, plan, input session, delegation instruction or evaluation-catalog entry is needed: like the M4/M5/M6 reads it is an orchestrator step (`ceo/cmo_history_chat.py`, `ceo/orchestrator.py`) behind the same `agent.cmo` permission and the CMO attachment check, and it records no metered event. The card kind is allowed by backend migration `20261031_0030`.

## 7. AI requirements

**LLM role in this feature is deliberately minimal.** The classifier selects a key and fills declared slot text (existing); every question, option, plan line, label, card and count is written by code from the registry, validators and stored rows; the result is posted verbatim by a fixed template (no composer call, orchestration §6.35). The CMO's own LLM use (title/copy writing, vision description, trend interpretation) is unchanged and remains behind its deterministic validators. The dashboard and its API call no model.

**Required evaluations** (`CLAUDE.md`; add the suites alongside the code, in the existing eval harness, orchestration §6.18). Each has a fixed scenario set and a pass criterion of zero violations on the committed set:
- **E-1 Unsupported attributes.** Across titles, bullets, description, keywords, hashtags and catalog answers: no output asserts an attribute that is not `SELLER_PROVIDED`, `IMAGE_OBSERVED` (gate passed) or `SOURCE_DERIVED`; an `UNVERIFIED_HINT` or `UNKNOWN` attribute is never stated as fact. Include a photo whose visible text names a material, size or certification the seller never confirmed.
- **E-2 Image labelling.** Every image-derived statement shown by the CEO carries "from your attachment" and the unverified/suggested wording while the gate is closed; the observation block contains only closed-schema fields; no inference appears in it; no numeral from an image appears as fact.
- **E-3 Disclaimers.** The artefact label (§6.7-1), the trend labels ("not a verified market fact", "attention, not demand"), the "not verified" label on suggested hints, the plan card's data-leaves-Metrion lines and the duplicate/uncertain-outcome warning are never dropped, shortened to omission or reworded to weaken.
- **E-4 No invention.** News items, source names, publication dates, "verified/official" badges, percentages and popularity/frequency claims appear only if present in the stored record or event counts. A section with no data produces the honest empty state, never a plausible item. (Applies to the dashboard fixture tests and to any CEO message that summarises the dashboard.)
- **E-5 Non-results are not results.** A `CLARIFIED` delegation, a `PLANNED` plan, a declined/expired/superseded plan, an `OUTCOME_UNKNOWN` turn and a failed artefact are never narrated as generated content or as a clean negative result.
- **E-6 No numbers outside the cited ones.** The delegation questions, plan card and result text contain no number except code-derived counts (characters, bytes, units, queries) and seller-stated values echoed verbatim.
- **E-7 Injection.** Text embedded in an image (`visible_text`), in an attachment's extracted text or in a seller's product name cannot add a requirement, fill a slot, approve a plan, change the endpoint or cause an extra leg.
- **E-8 Approval language.** No CEO reply states or implies that something ran, was approved or was charged before the requester used the card; a typed "yes" is never treated as approval.

## 8. Authorization and security

1. **Tenant isolation.** Every table read/written here is tenant-owned with `FORCE` RLS (the new §5.1 table, `investigation_attachment`, `cmo_*`, `investigation_*`). Missing tenant context fails closed. No endpoint, query string, body or card ever carries a `tenant_id`. A cross-tenant or cross-investigation `attachment_id` is a plain "not found". Frontend filtering is never a security mechanism (product selector and marketplace tabs are conveniences over server-side filters).
2. **Hand-off.** The agent re-validates the reference itself (§6.5-2); the CEO's pre-check is not trusted. An attachment from investigation A cannot be used in investigation B even in the same tenant. Bytes never appear in logs, messages, summaries, findings, plan rows or API responses; the plan stores the file's id/type/hash prefix only.
3. **Vision egress.** Only `LLM_OPERATOR_CONTROLLED_HOSTS` endpoints (§6.5-4); fail closed; no hosted vision provider (slim-cmo §6.2.2-1). The seller sees where the image goes before it goes (DD3).
4. **Permissions.** Chat: `agent.ceo` + `agent.cmo` (+ `files.upload` to attach, `catalog.view` for niche suggestions, `research.market_trends` for trends), per leg through the choke point; approval: requester-only (C7) and re-evaluated at approval. Dashboard: `agent.cmo`, read-only. No new permission key is introduced by this spec (consistent with approval Q-A4).
5. **No marketplace write, no direct execution from the dashboard.** The showcase issues only `GET`s (plus the usage-event telemetry `POST`, CD14); a test enumerates the frontend CMO components' network calls.
6. **Input safety.** Seller strings (product names, titles, file names) are escaped on display and never interpreted; the CMO forbidden-content scan runs before any plan (§6.2-3).
7. **Audit.** Delegation steps are CEO turns (`agent_run` anchors); plan transitions are the append-only `investigation_plan_event` history; usage events are append-only; none stores seller text.
8. **Privacy.** The shared attachment store keeps the original bytes (A4); retention and EXIF handling are an open policy (OQ-8). The usage-event table stores no text or content.
