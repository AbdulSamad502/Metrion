### B7 workflow review (listing generation and history), by reading the code and the existing tests
* **State transitions:** generation (a plan, 1 or 2 units, idempotent per request key) → audit (free, saved once per content hash) → seller edits/rewrites (new immutable version with `revision_of`) → approve for use (separate click, free, never publishes) → copied/marked used (separate events). Typed text never approves anything; every approval is a click bound to a plan id and hash or a card.
* **Persistence and lineage:** versions are insert-only; the history engine reports missing, cross-product and cross-marketplace parents; message order is now monotonic (`seq`).
* **Error handling:** a failed pack bills nothing and saves no listing; a failed backend-terms step after a good pack keeps the pack (PARTIAL); a refused edit/rewrite saves nothing; the over-limit and blocked-rules cases are refused before a plan card.
* **Gaps found and left as they are (documented, not defects of this scope):** a typed title's approval row is written when the listing is planned, so a declined plan leaves an approval (it is the seller's confirmed choice); the HTTP route that accepts a bare typed title records no approval; the CEO classifier path has no real-model evaluation (B2).

### B8 minimum reliable data architecture (design only; nothing fabricated, nothing built)
1. **Marketplace SKU → METRION product:** uploaded `sales_line` carries `marketplace`, `sku` (the seller's SKU in the report), `marketplace_item_id` (ASIN/FSN-type id), `item_title`, `order_date`, `quantity`, amounts and a confidence label. Metrion's product identity is the CMO `sku` slug. The only reliable bridge is a **seller-confirmed link table** (tenant, cmo sku, marketplace, report sku, item id, confirmed by/at; unique per tenant + marketplace + report sku), offered as a choice from the distinct SKUs and titles in the seller's own uploads. Never inferred from title similarity.
2. **Product → marketplace listing:** the same link row (one per marketplace).
3. **Listing → saved version:** already exists (`cmo_generation` lineage per product + marketplace).
4. **Version → go-live date:** Metrion cannot see the marketplace, so a **seller-stated go-live date per saved version** (append-only; a correction is a new row) is required.
5. **Sales → comparable periods:** deterministic engine only: equal whole-day windows immediately before and after the stated date, refused when another version goes live inside either window, when either window lacks sales-day coverage, or when the link is missing. Output is an observation with source, period and status, worded "seen alongside this version", never as impact or cause.
Until 1, 4 and 5 exist for a product, performance is NOT_ASSESSED with the missing item named (already the behaviour).
