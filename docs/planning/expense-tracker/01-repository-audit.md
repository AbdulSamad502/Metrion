## 1. Verified architecture, by area

### 1.1 CFO / Profit & Finance UI and navigation
- **[F]** Page `frontend/app/dashboard/cfo/page.tsx`, title "Profit & Finance" (`PAGE_COPY["cfo"]` in `frontend/lib/navigation.ts`). Six hash-addressed tabs (`CFO_TABS`): overview, profitability, cash, gst, anomalies, import. Each section is a client component calling a real `/api/v1/cfo/*` route (page comment: "nothing here computes or invents a figure").
- **[F]** The existing expense UI is `frontend/components/cfo/sections/ExpenseTrackerSection.tsx`, mounted in the **cash** tab ("Reconcile settlements to invoices, track expenses against a budget"). Offers five categories (`EXPENSE_CATEGORIES = advertising, packaging, storage, logistics, other`) and always writes `target_type: "ACCOUNT"`, `target_ref: "default"`.
- **[F]** UI conventions to reuse: `Section`, `Tabs`/`useHashTab`, `MetricCard`, `StatusBadge`, `EmptyState`, `ErrorNotice`, `CostInput` (explicit amount / none / unknown, no default) in `frontend/components/ui/` and `frontend/lib/costInput.ts`; exact-integer rupee→paise parsing (`toPaise` in `components/cfo/primitives.tsx`); guard tests that ban browser money arithmetic (`lib/noClientMath.test.ts`, `lib/noPnlClientMath.test.ts`).
- **[F]** The page contract is enforced by tests: request contract (`frontend/test-support/requestContract.json`, regenerated by `backend/scripts/export_request_contract.py`, checked by `backend/tests/unit/test_request_contract_snapshot.py`) and response contracts (`responseContracts.json`).
- **[F]** Expense Tracker is therefore naturally a section/tab inside the existing page, consistent with the brief ("not a new top-level navigation destination"). The Profit Calculator is a separate Business nav item and must stay separate (§1.12).

### 1.2 CEO chat, tool routing and CFO capabilities
- **[F]** The only conversational interface is the CEO (`auth.md` §5.2); CFO has "pre-enumerated, non-conversational" direct paths. There is **no CFO chat route** in `backend/src/backend/api/v1/cfo.py`.
- **[F]** `backend/src/backend/ceo/registry.py` defines `FORBIDDEN_ACTION_KEYS`, which includes `cfo.enter_expense` and `cfo.expense_budget_set` ("Write-class … must never be CEO-callable in V1 (spec C21, §6.11)"; registering one raises). `ceo/classifier.py` lists "recording expenses" under `OUT_OF_SCOPE`. Spec `ceo-agent-orchestration.md` C21 / E30 say the same: a request to "record this expense" is declined and redirected.
- **[F]** Confirmation infrastructure that exists is for **choices**, not writes: CEO decision cards (`frontend/components/ceo/hub/DecisionCard.tsx`, `DecidePanel.tsx`). The write-approval design `docs/specs/ceo-approval-workflow.md` is "Nothing in this spec is implemented"; `backend/src/backend/ceo/approval_gate.py` is **observe-only** ("imported by nothing in orchestration, chat, an API or execution" — its own docstring).
- **[F]** `agents/ceo_hub.py` has `dispatch_cfo_enter_expense` (deliberately leaves `financials.adjust` to its caller) and a family of `dispatch_cfo_*` functions that write a CEO `agent_run` with `trigger_type="DIRECT"`.
- **Consequence (as first audited):** chat quick-add conflicted with C21. **Update 2026-10-15:** the owner narrowed it to a draft that pre-fills vendor, category and date only; it was verified as reconcilable with C21/§6.33/§6.11 (E30/T36 amended). See `phase1-decisions.md` EXP-03.

### 1.3 Brain 1 — deterministic engine
- **[F]** Hard rule (CLAUDE.md, `docs/specs/deterministic-engine.md`): money is signed BIGINT paise, arithmetic only in `packages/calc-engine` (Python/SQL), no LLM in the path, missing input is `UNAVAILABLE` not zero.
- **[F]** Manual inputs live in one append-only table `manual_adjustment` (`packages/calc-engine/migrations/versions/20260917_0001_engine_tables.py`): columns `id, tenant_id, target_type, target_ref, field, value jsonb, reason, created_by, created_at, supersedes_id, status`; `FORCE` RLS tenant policy; `REVOKE UPDATE, DELETE … FROM metrion_app`. **There is no date, vendor, currency, payment-status, review-status or source-reference column.**
- **[F]** Writer: `calc_engine.repositories.manual_adjustment_repo.insert_adjustment` (tenant-checked supersede, requires same target and field). Service: `backend/src/backend/services/cfo_actions.py` — `_ALLOWED_MANUAL_ADJUSTMENT_FIELDS` (line 288: `cogs_per_unit`, `expense.advertising|packaging|storage|logistics|other`, `settlement.receipt`, `supplier.quote`, `batch.budget`), `enter_expense` (line 677; validates the field name only), `list_expenses` (line 1351), `set_expense_budget` (line 1436).
- **[F]** Value shape and parsing: `calc_engine.formulas.expense_pools.parse_expense_pool_adjustment` — `{amount_paise, gst_amount_paise?, marketplace?}`; runs on **read**, so a malformed stored row breaks listing (B4).
- **[F]** Allocation: `calc_engine.formulas.allocation.allocate_pool`, `AllocationBasis` (`NET_REVENUE | UNITS | ORDERS`); `expense_pools.allocate_account_level_expense_pool`. Spec decision D7: account-level costs allocated **by net revenue share, automatically**, result always `DERIVED`.
- **[F]** The period P&L: `cfo_actions.compute_period_pnl` takes `advertising_adjustment_values` and `other_adjustment_values` (lines 355–356, 453–454) and sums them with `cfo.pnl.inputs.resolve_expense_pool_total`. **Both lists are request-body inputs** (`api/v1/cfo.py` 955–956, 1010–1011, 1046–1047, 1084–1085). **No code reads stored `expense.*` rows to build them** (repository-wide grep, this run). So a saved expense does **not** move Contribution Profit by itself, and `expense.packaging|storage|logistics` have no consumer in the period P&L (B2).
- **[F]** Engine documents an explicit exception to "missing is not zero": advertising/other spend that is absent resolves to **zero** (`resolve_expense_pool_total` docstring; `deterministic-engine.md` §5.6 line ~289). The brief says "never treat unknown amounts as zero". Recorded as decision D1-c.
- **[F]** Reproducibility: `metric_result` rows carry `formula_version`, `config_version`, `canonical_data_version`, `manual_adjustment_set`, `as_of_date`, `computed_at` (engine §4.2; migration lines 57–79).

### 1.4 COGS, advertising, settlements, fees, refunds, returns, GST, margin
- **[F]** COGS is `cogs_per_unit` (SKU grain, effective-dated, weighted average) — a **unit** input, writable through the same `PUT /cfo/expenses` route. It is not a lump-sum expense.
- **[F]** Settlement-derived costs are canonical `line_component` rows written by marketplace adapters: `packages/data-foundation/src/data_foundation/adapters/` (`amazon_settlement_v2`, `amazon_mtr_*`, `flipkart_payments_v1`, `flipkart_sales_report_v1`, `meesho_*`). **There is no advertising-report adapter.** The Flipkart payments adapter maps `Non-Order Charges` (`NON_ORDER_FEE`, described in `component_registry.py` as "advertising / storage"), so settlement data can already contain ad/storage cost.
- **[F]** Cash/TCS: `calc_engine.api.cash_reconciliation` (`CASH_RECEIVED`, `TCS_COLLECTED` for Flipkart; `TDS_DEDUCTED` unavailable), explicitly a settlement-basis view, never P&L (engine §5.13.3).
- **[F]** GST is management-grade, not filing-grade (`cfo-agent.md` C4/§6.6). No GST rate is hard-coded in the expense path.
- **[F]** The Profit Calculator (`POST /api/v1/cfo/pnl-scenario`, `calc_engine.formulas.pnl_scenario`) is a hypothetical estimator with its own "operating expenses per month" input; it does not read or write `manual_adjustment`. Spec `calculator.md` Q8 records that pre-filling it from tracked data is deliberately not done.

### 1.5 Tenant / organization model and active-organization resolution
- **[F]** One Clerk Organization = one tenant (CLAUDE.md). `backend/src/backend/auth/context.py::resolve_auth_context`: the active organization is the **`org_id` claim of the verified Clerk JWT**; `tenant_repo.get_by_clerk_org_id` maps it to `tenant_id`; membership must exist and be `ACTIVE`; role must be `OWNER` or `PARTNER`; `has_permission` checks the required key (OWNER bypasses). No `org_id` ⇒ `PENDING_ONBOARDING` (403 on every guarded route). No route accepts a client-supplied `tenant_id` (CLAUDE.md; `pnl-scenario` rejects it explicitly with `extra="forbid"`).
- **[F]** Database boundary: `FORCE ROW LEVEL SECURITY` with `current_setting('app.current_tenant_id')`; every query runs inside `tenant_scope(tenant_id)`. `supersedes_id` is verified against the caller's tenant.
- **[F]** Weak point carried from the earlier audit (B10): several read queries (`_ACTIVE_FOR_TARGET_SQL`, `_ACTIVE_BY_EXACT_FIELD_SQL`, `_ACTIVE_BY_FIELD_PREFIX_SQL`) rely on RLS alone with no explicit `tenant_id` predicate, against CLAUDE.md's "neither is trusted alone". Not exercised this run.

### 1.6 Authentication, authorization, financial permissions
- **[F]** `auth.md` permission grid: `agent.cfo`, `financials.adjust` ("Create or supersede manual financial adjustments — every field in the §7.2.1 registry, without exception"), `report.download`, `files.delete` and others. OWNER holds every key implicitly; **`financials.adjust` is deny-by-default for PARTNER**; "a partner without it may still upload files and view figures".
- **[F]** `PUT /cfo/expenses` (`api/v1/cfo.py::put_expense`) requires `agent.cfo` (dependency), the CFO entitlement (`_require_cfo_entitlement`, `cfo.enter_expense`) and `financials.adjust` (in-handler `has_permission`). `GET /cfo/expenses` requires only `agent.cfo` and no entitlement check. There is **no separate read permission for financial data**.
- **[F]** Because the key covers **every registry field**, granting a partner `financials.adjust` for expenses also lets them write `cogs_per_unit`, `settlement.receipt`, `supplier.quote`. A narrower key would be an `auth.md` change (decision D11).

### 1.8 CSV import, upload, storage, parsers, duplicate detection
- **[F]** `POST /cfo/ingest` (`api/v1/cfo.py::post_ingest`): `backend.uploads.read_upload_capped`, SHA-256 file dedupe (`report_file_repo.find_by_content_hash(tenant_id, hash)` → `{duplicate: true}`), adapter registry (`ADAPTER_REGISTRY`), `ingest_and_persist`, `ingestion_run` counters (`row_count_*` incl. duplicates). It **persists immediately; there is no preview/dry-run**, and it handles marketplace report adapters only (no expense adapter).
- **[F]** Storage is **local disk**, `cfo_report_storage_dir()`, file name = content hash + suffix, in **one directory shared by all tenants**; `storage_uri` is never returned by `report_file_repo`; no download endpoint. There is no object storage (`backend/src/backend/config.py` comment: real object storage is later).

### 1.9 Local vision / OCR
- **[F]** A vision slot exists: `VisionProvider` Protocol (`packages/slim-cmo/src/slim_cmo/vision/provider.py`: `describe(model, schema_version, image) -> str`), `OllamaVisionProvider` (`slim_cmo/providers/ollama_vision.py`), `ScriptedVisionProvider` for tests, wired in `backend/src/backend/services/cmo_runtime.py`. It describes **product images** for the CMO; it is not an OCR/receipt extractor. Receipt OCR (V1.5) would reuse the slot but needs its own schema, evals and storage (out of scope).

### 1.10 Tests, API contracts, background jobs, recurring work
- **[F]** Conventions: pytest unit tests that call routes as plain functions with fakes (`backend/tests/unit/test_cfo_route_entitlement_enforcement.py`, `test_cfo_pnl_scenario.py`); scratch-Postgres integration tests (`backend/tests/integration/`, `scripts/scratch_db.sh`, `db_guard.py` refuses the dev DB); every-route 401 (`test_every_route_requires_auth.py`) and 403 (`test_every_route_permission.py`) parametrised over the OpenAPI document; calc-engine unit/property tests (`hypothesis`); frontend Vitest + Testing Library with the request-contract guard in `test-support/setup.ts`.
- **[F]** Existing expense tests (names only): `packages/cfo/tests/unit/test_cfo_actions_expense*.py`, `packages/calc-engine/tests/unit/test_expense_pools.py`, `packages/calc-engine/tests/integration/test_manual_adjustment_append_only.py`.
- **[F, correction to the earlier audit]** There **is** an in-process periodic worker mechanism: `backend/src/backend/main.py` starts background threads (`_sweep_ownerless_runs_forever`, interval from `config.recovery_sweep_interval_seconds()`, plus a periodic CEO-leg settler). It is a recovery sweep, not a general scheduler, and runs per worker process; there is **no cron, queue or scheduler library** (no apscheduler/celery/arq/rq in any `pyproject.toml` or import). Redis is used only by `backend/ceo/event_bus.py` and `state_cache.py`, not as a job queue. Recurring expense templates therefore need a defined materialization design (roadmap phase P4); the existing thread pattern is the only precedent.

## 3. Missing capabilities

## 4. Architecture conflicts (need a decision before design)
1. **C21 vs quick-add** (D3).
2. **`manual_adjustment` cannot hold the draft's fields** vs the recorded decision that `expense_entry` tables were **removed by design** (`cfo-agent.md` line ~113) (D1, D2).
3. **Absent ad/other spend = 0** in the engine vs the brief's "never zero" (D1-c).
4. **D7 automatic revenue-share allocation** vs the brief's "business-level by default; allocate only when explicitly selected" (D9).
5. **IndiaMART** is a supplier-discovery source (`product-intelligence-agent.md` C5/C6, schema-only), not a sales channel with settlement data (D14).
6. **"30-day rule" and `legal-safeguards.md`** are cited but absent (D12).
7. **`currency`**: the engine is INR-paise only.
8. **Shared-directory, content-hash storage** is unsuitable for receipts (B10 weak 2).
