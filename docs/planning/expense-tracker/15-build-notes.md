### S3b — repository, rules, service routes (backend)

- Every route has `agent.cfo` + the CFO entitlement gate (codes `cfo.expense_ledger.read|write`; no cap configured, so they pass until the owner configures one); every write also needs `financials.adjust` in the handler (no new key). One `agent_run` row (`DIRECT`, `cfo.expense_ledger`) per write that changes the ledger; an idempotent replay writes nothing and no run row; a request rejected at the edge (422/403/404) writes none. - Manual entries default to review state `confirmed` (the person entering it is the reviewer) and payment status `unknown`; the caller may create `draft` or `pending_review`. This default is an implementation choice for owner review.

### S4a — ledger feeds the period P&L, default OFF (commit 2c1c03a)
- Flag `EXPENSE_LEDGER_FEEDS_PNL` (`backend/src/backend/config.py`, default off, not cached). Off: `compute_period_pnl_for_tenant` reads no ledger row and every result and response is exactly what it was (`test_flag_off_changes_nothing_and_reads_no_ledger` makes the feed fail if it is called; the response gains no key). On: the engine feed (`ledger_feed`) supplies the advertising term (ADVERTISING pool) and the other-attributed term (DIRECT pool); a caller-supplied advertising or other entry wins and the ledger's is reported as skipped, so nothing is counted twice. STORAGE and OVERHEAD are NOT put into contribution profit: they come back as unallocated lines (`UnallocatedStorage`, `UnallocatedOverhead`) labelled `CONTRIBUTION_PROFIT.v1`, each with an `engine_result_ref` (engine §5.17 cost-class mapping: v1 has no storage term; the explicit `StorageCosts` term belongs to the inactive v2). A class with no counted row is "not entered", never zero. Only confirmed, non-voided, incremental rows count; a refund reduces the pool by its own signed amount; `already_in_settlement` and `informational` rows are excluded.
- Response block `expenseLedger` on `POST /cfo/pnl-for-tenant`, only when the flag is on. Tests: `backend/tests/integration/test_expense_ledger_pnl_feed.py` (8: flag off, flag spellings, feeds and unallocated lines, nothing entered, review states and sign mapping, double-counting protection, reconciliation with the dashboard feed, response block). `CONTRIBUTION_PROFIT.v2` is not persisted.

### S4b — recurring, amortized and per-order/per-unit templates (commit d7d32e8; ended-template fix in ea0bf1e)
- Engine `calc_engine/formulas/expense_templates.py` (amortization by largest remainder, remaining balance, per-count amount, rate versions); tests AM1–AM5, PT1–PT5, PT7 in `tests/unit/test_expense_templates.py` (22). Migration `20261022_0014_expense_template` (immutable versions, FORCE RLS, UPDATE/DELETE revoked). `expense_template_repo.py` materialises entries into the ledger as `pending_review` (X10) records dated the first of the month, flagged `recurring`, with the idempotency key `template:<key>:<yyyy-mm>` (materialising twice creates nothing twice; a voided entry is not recreated). Routes under `/cfo/expense-ledger/templates` (list, create, new version, end, materialise) with the ledger's gates.
- Deviations and limits for owner review: (1) amortization is stored as a template and materialised as one entry per month (that month's share), not as record-level `amortization_*` fields; totals are identical, AM6 follows from voiding or ending, AM7 (a refund reducing the remaining schedule) is not implemented, AM8 is covered by the pool-total invariance in the feed tests. (2) Per-order and per-unit templates are stored but never materialised: the engine's order and unit count (§5.10.1) is not available from `CanonicalLine` (it has no order id), so they are reported as skipped with `ORDERS_UNAVAILABLE` / `UNITS_UNAVAILABLE`, never as zero; PT6 and PT8 wait for a count source. (3) An amortized template uses the amount and months of its first version. (4) Materialising is bounded to next month at most and 120 months per template (PROPOSED).
- Tests: `test_expense_template_repo.py` (14), `test_expense_templates_api.py` (29).

### S5a — CSV import (commit ea0bf1e)
- Fixed 7-column template (`date,vendor,description,category,amount_rupees,source_id,channel`) from `GET .../import/template`. `POST .../import/preview` writes nothing (no ledger row, no run row) and reports every row (OK, ERROR with reasons, DUPLICATE by source id, PROBABLE_MATCH). `POST .../import/commit` writes accepted rows as `pending_review`, `origin = IMPORT`, keyed `import:<sha256>:<row>` (a re-upload creates nothing twice); a file with invalid rows is refused whole unless `skip_invalid=true`; probable matches (same date, normalised vendor, amount and description) are written and flagged in `source_reference` (`...:probable:<id>`), never dropped; exact source-id duplicates are skipped and listed. Confirmation is the ordinary review action (`financials.adjust`). No raw CSV is stored: only the parsed fields and the source id or `import:<first 12 of the SHA-256>:row<n>`. Rupees become paise by digit handling (no float); imports are costs only (a refund goes through the refund action). The template has no SKU or identifier columns, so imports are business-level (Q29).
- Tests: `tests/unit/test_expense_import.py` (56) and `tests/integration/test_expense_import_api.py` (17).

## Proposals for owner review (R9-5)
All limits live in `backend/src/backend/services/expense_ledger_rules.py` (single place to change) and are served to the UI by `GET /cfo/expense-ledger/categories`:
| Limit | Value | Basis |
|---|---|---|
| Amount magnitude | 9,999,999,999,999 paise (11 rupee digits) | existing: `frontend/lib/pnlText.ts` and the Profit Calculator API ceiling |
| Amount type | integer paise, not bool/float/string; zero allowed; a cost is ≥ 0, a refund < 0 | existing: `parse_expense_pool_adjustment`; Q21 |
| Vendor / description / reason | 120 / 500 / 500 characters | PROPOSED (no equivalent in the legacy route) |
| SKU / source reference / idempotency key | 120 / 200 / 120 characters | PROPOSED |
| Page size | default 50, maximum 200 | PROPOSED |
| Vendor text (Q22) | refuse a currency symbol or code, a grouped or decimal number (1,200.50), or five or more digits; allow short numerals | Q22 decision; exact pattern is the implementer's, PROPOSED for review |
| Date | a valid ISO date; no future-date or age limit | none exists in the legacy code, so none is invented |
| CSV import size / rows | 1 MB and 2,000 rows per file | PROPOSED (S5a) |
| Import source id | up to 80 characters of letters, digits and . _ / # : - | PROPOSED (S5a) |
| Templates | amortization 1 to 120 months; materialise at most to next month; a template may span at most 120 months; no start before 2000-01-01 | PROPOSED (S4b) |
| Multi-SKU assignment | at most 20 SKUs per expense | PROPOSED (S5c) |
(These are the X2 proposals: E9 in the decisions register stays open until the owner acknowledges them.)
