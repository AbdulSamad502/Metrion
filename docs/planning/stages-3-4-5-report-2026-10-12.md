## R5 (full report: `docs/planning/r5-stuck-running-findings-2026-10-12.md`)
Root cause: a `RUNNING` row proved nothing about an owner, and only seller-turn anchors were recoverable. Fixed with lock-based ownership (taken before the row, released after the terminal write; process death ends the session and the lock), a sweep that never dispatches or retries, guarded writes so competing sweepers and late finishers cannot corrupt a result, and settle-on-exception for the direct dispatchers. Uncertain external effects are not repeated and not assumed: the seller is told the request was interrupted. **Closure pass:** the same mechanism now covers `reconciliation_run` and `ci_capture_run` (through ownership hooks the backend plugs into the packages) and CMO requests (row opened at the first model call, so rejected requests still persist nothing); a periodic sweep (default every 300 s, configurable, 0 = start-up only) removes the "only at next start-up" gap. **R5 is resolved for every run table that starts RUNNING;** the remaining limits (older-worker deploy precondition, tenant-level PI rule, CMO reservation TTL) are in the R5 document.

Recovery of a killed run: the sweep itself takes milliseconds (above); it now runs at every start-up AND every `RECOVERY_SWEEP_INTERVAL_SECONDS` (default 300 s), so a dead worker's rows wait at most one interval plus one pass. Queue wait and worker count are **not measured**: there is no queue (turns run in the request process). Pool: SQLAlchemy's own defaults (5 + 10 per engine, 30 s wait) kept deliberately and made overridable (`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_POOL_TIMEOUT_SECONDS`); there are 7 engines per process (backend plus 6 packages), each with its own pool, and the liveness connection and every held turn lock each occupy a pooled connection. The only NEW default is the 10 s connect timeout: a local connection takes milliseconds, so it only ever fires when the database is stalled or unreachable; it needs no load test, unlike pool sizes, for which no recommendation is made without one.

**Dependencies that shape any erasure.** (1) `investigation_finding`, `investigation_message`, `investigation_turn` and `metered_event` all reference `agent_run` with NO ACTION: a run cannot be deleted while the ledger still points at it, so erasing a conversation and keeping the ledger needs either `ON DELETE SET NULL` on `metered_event.agent_run_id` (a schema change) or keeping a content-free `agent_run` shell. (2) Delete-order cycles were already removed from the CEO tables for this purpose (spec ceo-agent-orchestration.md, migration 20261007_0006); one CMO cycle (`cmo_generation` and `cmo_title_option`) is known and needs deferred constraints. (3) Only 7 foreign keys reference `tenant`, so tenant-wide erasure is a per-table `DELETE ... WHERE tenant_id` under RLS in dependency order, not a cascade. (4) Append-only privileges (findings, memory, audit, ledger) mean erasure can only be done by the owner role, never by the running application: that is a feature. (5) Files on disk (CFO uploads, CI evidence, CMO images) are not covered by any database operation. (6) Shared findings and the forgotten-memory rows contain the original seller text.

**Options.**
* **A (recommended): erase on request by an operator routine.** Two triggers only: the seller asks to forget a conversation or memory item (physical erase of content rows and files, not a tombstone), and account closure (erase all content). Always kept, content-free: `metered_event` and `auth_audit` for the legal period. Needs: an owner-role `erase_tenant`-style script (dry run first, dependency order, one transaction, an audit record, file removal), `ON DELETE SET NULL` on the ledger reference, and a REVOKE of the remaining UPDATE/DELETE grants on evidence tables (the app then never deletes anything). Consequence: the seller's request is honoured fully; the accountant's records survive; effort is one routine plus one migration.
* **B: keep everything until account closure, then erase everything.** Simplest to build and explain, but "forget" stays logical (the text remains in the database until the account closes), which may not satisfy an erasure request under DPDP; no data minimisation during the account's life.
* **C: status quo (logical forgetting only, nothing erased).** No work, no privacy promise beyond "hidden from recall"; the spec itself calls true erasure "needed before launch".
No legal retention period is proposed here: that is for counsel (DPDP, accounting/GST record keeping).
