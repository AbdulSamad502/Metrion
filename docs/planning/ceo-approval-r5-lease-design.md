# R5 per-leg ownership, fencing and recovery: design proposal

Date: 2026-10-10. Status: **design proposal for owner review. Documentation only: no code, schema, migration, test, billing, permission or configuration change; nothing here is accepted, and no timing has been measured.** Builds on `ceo-approval-r5-feasibility-audit.md` (lifecycle facts L1-L10, gaps G1-G8, tests T1-T11), `ceo-approval-remediation-design.md` (R5, R6) and `ceo-approval-s1-readiness.md` (D-6). Where this document and design R5.2/R5.6 differ, this proposal is what is offered to replace them; the owner decides (§10).

**What is invented and what is not.** No lease duration, heartbeat interval, deadline or staleness threshold is proposed anywhere. The design is built so that liveness and authority are decided **by events and by database state, not by a bare timeout**. Where a duration would be unavoidable (heartbeat fallback, reservation extension) it is named as a decision and the existing configured TTLs are reused, not new numbers.

---

## 1. Principles
1. **Ownership is not liveness, and liveness is not authority.** Three separate things: *who runs the leg* (owner), *is that owner alive* (session-level advisory lock held), and *who may still write results* (a **fencing token**, an integer epoch stored in the database and checked in the same transaction as every write that matters).
2. **A lock alone does not fence a running worker.** A worker that has lost its lock (dropped connection, revocation) keeps executing Python until it notices. The design therefore fences at every *boundary* a worker crosses: (a) before the first external call, (b) before each further external call, (c) at every durable write that affects billing, findings or status. A call already sent cannot be recalled (§5.4); the design bounds the uncertainty to that one call and records it, it does not pretend to cancel it.
3. **Recovery never dispatches.** The reconciler imports no dispatch or registry invoker; it only moves rows between recorded states, releases quota it is entitled to release, and repairs missing writes **from stored decisions and durable domain rows** using the existing idempotency keys.
4. **At most once, with explicit uncertainty.** A leg is dispatched at most once per request key. If it is unknown whether an external request left Metrion, the state says so (`OUTCOME_UNKNOWN`), the seller is told, nothing is retried and nothing is charged by recovery.
5. **First writer wins, and the loser is told.** Every transition is a compare-and-set; a rejected write is logged with the reason and never silently overwrites.

## 2. Ownership model

### 2.1 The lease row (new table; requires a migration, §9)
One row per leg dispatch, created by the dispatcher **before** the leg's own rows exist, so it also exists for CMO (which writes no in-flight `agent_run`, audit L6). Working name `ceo_leg_lease`.

| Column | Meaning |
|---|---|
| `id uuid pk` | generated by the dispatcher; **also the advisory-lock key** (`hashtextextended('leg:'||id, 0)`), so the reconciler needs no derivation |
| `tenant_id`, `investigation_id`, `anchor_run_id` | RLS key, the turn's CEO anchor run |
| `action_key`, `external_capable bool`, `metered bool` | copied from the R1 registry metadata at claim time (the classes that decide recovery behaviour) |
| `request_key text` | the leg's idempotency key (`ceo-<card or message id>` for CMO; the PI request key); `NULL` for internal legs |
| `state`, `epoch bigint` (>= 1), `owner_id uuid` | §3; `owner_id` is a random per-process id, for diagnostics and to show a stale owner in logs |
| `claimed_at`, `effect_started_at`, `finished_at` | **database `now()`**, never the application clock |
| `leg_run_id uuid null`, `reservation_ref` | the leg's `agent_run` (once it exists) and the quota reservation key it holds, so recovery can find both |
| `reason text`, `recovery jsonb` | refs only; never figures or seller text |

Constraints: `UNIQUE (tenant_id, anchor_run_id, action_key)` (a turn cannot dispatch the same leg twice); a **partial unique index** on `(tenant_id, action_key, request_key) WHERE state IN ('CLAIMED','EFFECT_STARTED')` (a second live request with the same key is "in progress", the existing `RequestInProgress` pattern; closes cross-turn duplicates); `CHECK` that terminal states carry `finished_at`; FORCE RLS + `tenant_isolation`; application role `SELECT, INSERT` and column-level `UPDATE (state, epoch, effect_started_at, finished_at, leg_run_id, reservation_ref, reason, recovery)`; no `DELETE`, `TRUNCATE`, or `UPDATE` of identity columns. An append-only `ceo_leg_lease_event` table (actor, from/to, epoch, reason code) is recommended for audit parity with spec C10 (decision D-L9).

### 2.2 Acquisition (order is the safety property)
1. Dispatcher generates `lease_id`.
2. Opens a **dedicated autocommit connection** (the existing `AdvisoryLock` class) and takes `pg_try_advisory_lock(lease_id)`; failure here cannot happen for a fresh id and is treated as a bug.
3. **Only then** inserts the lease row `CLAIMED, epoch = 1`. A reconciler can therefore never see a row whose lock was not already held by its creator: no window with a row and no owner.
4. Registers `Lease(lease_id, epoch, conn)` in a contextvar for the leg's thread, as `agent_run_repo.parent_run_scope` already does for the parent run.
Crash points: after 2, before 3 (no row; lock freed; nothing to recover); after 3 (row `CLAIMED`, lock freed on session end: recoverable, §6.1).

### 2.3 Renewal
**Session lock: none needed.** The lock is held by the connection for as long as the worker lives; there is nothing to renew and therefore no duration. A heartbeat (touch `last_seen` at an interval, expiry by a lease TTL) would need exactly the durations this design avoids; it is offered only as an **alternative for deployments where session locks are unreliable** (transaction-mode pooler, G7) and is decision D-L2. The quota reservation, which has its own TTL, is **extended at each boundary** by its already-configured TTL (§7.2); that reuses an existing number and needs no new one.

### 2.4 Loss detection (event-driven)
`lease.check()` is called at every boundary (§5). One round trip on the lock connection: (a) the connection is alive and still holds the advisory lock (`pg_locks` for this backend), and (b) `SELECT epoch, state FROM ceo_leg_lease WHERE id = :id` equals the worker's `epoch` and a non-terminal state. Any other result raises `OwnershipLost`; the worker stops, performs no further external call or write, and returns a leg result of status `ABANDONED` (never `COMPLETE`). The worker **never re-acquires** a lost lock: lost means lost.

### 2.5 Terminal release
Order: the fenced completion transaction commits (§5.3), **then** the advisory lock is released and the connection closed (`finally`). A crash between commit and release is harmless (lock dies with the session; state is already terminal). A crash before the commit leaves a non-terminal row with a free lock: recoverable.

## 3. State machine (lease row)

```
             claim (lock held, epoch=1)
                    │
                    ▼
   ┌──────────── CLAIMED ──────────────────────────────────────────┐
   │   │ marker (fenced; BEFORE the first external-capable call)   │
   │   ▼                                                           │
   │ EFFECT_STARTED                                                │
   │   │                                                           │
   │   ├─ owner completes ─────────────► SUCCEEDED   (terminal)    │
   │   ├─ owner fails deterministically ─► FAILED     (terminal)    │
   │   │                                                           │
   │   │  owner dead / lock lost / revoked, recovery:              │
   │   ├─ durable domain row proves completion ─► SUCCEEDED_ADOPTED (terminal)
   │   └─ otherwise ──────────────────► OUTCOME_UNKNOWN (terminal) │
   │                                                               │
   │  owner dead / revoked while still CLAIMED (nothing sent):     │
   └──────────────────────────────────────► NOT_DISPATCHED (terminal)
   internal (not external_capable) legs: no marker; dead mid-leg ─► INTERRUPTED (terminal)
```
Terminal: `SUCCEEDED`, `SUCCEEDED_ADOPTED`, `FAILED`, `NOT_DISPATCHED`, `INTERRUPTED`, `OUTCOME_UNKNOWN`. Nothing leaves a terminal state; the database enforces it (constraint trigger, decision D-L6; without it this is code discipline only, the same Q-A10 trade-off as for plans).

| Transition | Actor | Guard (all in the `WHERE`) | Notes |
|---|---|---|---|
| (none) → `CLAIMED` | dispatcher | lock held | §2.2 |
| `CLAIMED` → `EFFECT_STARTED` | owner | `id = :id AND epoch = :mine AND state = 'CLAIMED'`, 0 rows ⇒ `OwnershipLost`, **abort before the call** | sets `effect_started_at = now()`; autocommit, durable before any external bytes leave |
| `CLAIMED`/`EFFECT_STARTED` → `SUCCEEDED`/`FAILED` | owner | `epoch = :mine AND state IN (...)` **inside the completion transaction** | §5.3 |
| `CLAIMED` → `NOT_DISPATCHED` | recovery | lock acquired by the reconciler **and** `state = 'CLAIMED'` | `epoch = epoch + 1` (revokes any zombie) |
| `EFFECT_STARTED` → `OUTCOME_UNKNOWN` | recovery | lock acquired, no durable completion evidence | `epoch + 1`; **no usage, no retry** |
| `EFFECT_STARTED` → `SUCCEEDED_ADOPTED` | recovery | lock acquired **and** the specialist's durable terminal row exists (§6.4) | `epoch + 1`; repairs only what is missing |
| `CLAIMED`/`EFFECT_STARTED` (internal) → `INTERRUPTED` | recovery | lock acquired | safe to recompute in a new, newly approved plan |
| `CLAIMED`/`EFFECT_STARTED` → revoked | **turn deadline** (§5.5), only for metered/external legs, if the owner approves D-L3 | `epoch = :mine` | `epoch + 1`; the owner's next boundary raises `OwnershipLost` |

## 4. Turn-level coupling
The investigation turn lock (audit L1) remains the liveness proof **for the turn** (a free lock ⇒ no live turn owner), valid for the "turn row non-terminal" and "approved, never started" cases. It is **not** consulted for legs. A turn is reconciled only when its own lock is free **and** every one of its lease rows is terminal or recoverable; a leg still held by a live owner keeps the turn row unfinalised only if the turn is itself dead (the late-leg case: the turn finalised normally, the leg continues under its own lease).

## 5. Fencing: how a live worker is kept from doing harm after losing ownership

### 5.1 What can and cannot be fenced
| Side effect | Fenceable? | Mechanism |
|---|---|---|
| Durable writes (leg `agent_run` terminal, finding, usage event, reservation settle, turn update) | **Yes** | epoch compare-and-set in the **same transaction** (§5.3); a stale owner's transaction rolls back |
| An external call **not yet started** | **Yes, cooperatively** | `lease.check()` immediately before the call (§5.2); a TOCTOU window of one call remains (revocation lands between check and send) |
| An external call **already in flight** | **No** | cannot be recalled; the lease already says `EFFECT_STARTED`, so the outcome is recorded as uncertain (`OUTCOME_UNKNOWN`) and never retried |
| Provider-side exactly-once | **No** | none of Tavily, YouTube, Google Places or the model endpoint is keyed with an idempotency key in the code; this cannot be added from Metrion's side |

### 5.2 Pre-effect boundary
A thin guard (`lease.before_external_call()`) is called at each external-call seam. The first call does the `CLAIMED → EFFECT_STARTED` marker (fenced, durable, before any bytes leave); later calls do `check()`. If the check fails the worker raises `OwnershipLost` **before** calling. This needs a **worker change at every seam** (the HTTP clients and model calls inside the PI and CMO packages and the GST fetcher); an inventory of seams is a prerequisite (D-L8). Until a seam is guarded, that leg class is only fenced at its **write** boundaries, and its design guarantee degrades to "no stale write, possible extra external calls up to the next guarded boundary", which must be stated per agent, not assumed.

### 5.3 Completion transaction (the stale-owner gate)
> **Superseded by §14.1a:** a single transaction is not available (each repository opens its own `tenant_scope`); the completion is a fenced sequence of idempotent writes with the lease terminal state written last.
One database transaction, in this order:
1. `UPDATE ceo_leg_lease SET state = :terminal, finished_at = now() WHERE id = :id AND epoch = :mine AND state IN ('CLAIMED','EFFECT_STARTED')`; **0 rows ⇒ roll back the whole transaction and raise `OwnershipLost`** (this statement is the gate; everything below is inside the same transaction and so is discarded with it).
2. Guarded leg `agent_run` terminal write (`WHERE status IN ('QUEUED','RUNNING')`).
3. Finding insert, made idempotent (a unique `(turn_id, action_key)` guard or `NOT EXISTS`; decision D-L7).
4. Usage events with their existing keys (`pi:run:<run_id>:<meter>`, per-artefact CMO keys); `ON CONFLICT DO NOTHING` on `(tenant_id, idempotency_key)`, the constraint that already exists.
5. Reservation `SETTLED`/`RELEASED` (existing guarded `WHERE state = 'RESERVED'`).
Today steps 2-5 happen in several independent transactions inside specialist code (PI `post_discover`, `settle_discover`; CMO `_record_run` and usage recording). Moving them behind the gate is a **worker change** for PI and CMO (D-L8). For CFO and CI legs written by the choke point itself, `dispatch()` can do it alone.

### 5.4 Residual risk (stated, not hidden)
After a hard kill or a lost lock, up to **one external call per live worker thread may already be in flight**. The design guarantees it is recorded as uncertain, never repeated, never charged by recovery, and surfaced to the seller. It does not and cannot guarantee that the provider did nothing.

### 5.5 The turn deadline and late legs (policy decision D-L3)
> **Superseded by §14.2:** the code review recommends **not** revoking at the turn deadline by default (revocation cannot stop an in-flight call and would create unbilled usable results); the text below is kept as the original proposal.
Audit L2/L8: today a leg that outlives `leg_timeout_seconds` keeps running and later writes its finding and any usage. Proposal by effect class:
- **Internal, unmetered legs** (CFO computation, CI price scenario, `pi.report`, preview): unchanged. They may finish late under their own lease; the guarded completion writes their finding; no usage exists to be inconsistent.
- **Metered or external-capable legs** (the actions D-8 currently blocks, and any approved execution): at the deadline the orchestrator **revokes** the lease (epoch bump) for any leg still running. The owner's next boundary raises `OwnershipLost`; if it was in flight the state ends `OUTCOME_UNKNOWN`. A metered leg therefore can never be charged after the turn already showed it as failed (closes audit G4).
This is a behaviour change for approved execution only; it is the owner's call because it trades "late results arrive" for "billing and the turn's record always agree".

## 6. Recovery outcomes
Recovery is a standalone one-shot CLI plus a bounded lazy trigger (unchanged from design R5.1). For each non-terminal lease row it first tries `pg_try_advisory_lock(lease.id)` on its **own** connection and holds it while it transitions the row. Not acquired ⇒ a live owner exists: skip, report `skipped_live`. No age or threshold is used to decide liveness.

1. **Proven not dispatched** (`CLAIMED`, lock free): the marker was never written, so no external bytes left. → `NOT_DISPATCHED`, `epoch + 1`; release the leg's reservation (`RESERVED → RELEASED`, existing guarded SQL); close a leg `agent_run` left `RUNNING` by the choke point as `FAILED`/`NOT_STARTED`; no usage. If every leg of a dead execution turn is `NOT_DISPATCHED`, the turn becomes `FAILED` (`EXECUTION_NOT_STARTED`) with the plan consumed (spec §6.8 rule 1).
2. **Still owned by a live worker** (lock held): no change. The late-leg case (the turn finalised, the leg alive) lands here until the owner completes under the gate.
3. **External side effect, uncertain** (`EFFECT_STARTED`, lock free, no durable completion): → `OUTCOME_UNKNOWN`, `epoch + 1`; leg `agent_run` `FAILED` with `error_reason = OUTCOME_UNKNOWN`; reservation **released** (quota protection only; it was never a billing record); **no usage event**; the turn's recovery record names the leg; the next plan for the same action carries `prior_attempt: UNKNOWN` (spec §6.8 rule 3). Nothing is retried.
4. **Completed work with a missing or incomplete parent update:** the specialist's own durable terminal row is the evidence of completion: PI `pi_research_run.status = 'COMPLETE'` with its stored `usage_due`; CMO artefact rows `COMPLETE`; a leg `agent_run` already `COMPLETE`. If such evidence exists the row becomes `SUCCEEDED_ADOPTED` and recovery performs **only the missing, idempotent writes**: guarded `agent_run` terminal, finding (idempotent), and **usage solely from the stored decision** through the existing key, so a late owner and a repair cannot both bill. If the parent turn is non-terminal and its own lock is free it is finalised `FAILED` with a recovery record and **no composed answer** (recovery calls no model); the completed finding stays visible; the CEO unit is NOT_DUE (turn not delivered), while the specialist's own usage follows its own rule.
Each outcome writes one `ceo_leg_lease_event` (recommended) and a recovery record on the lease row.

## 7. CMO and PI specifics
### 7.1 CMO's missing in-flight row
With the lease row created at claim time, a killed CMO leg is visible: `CLAIMED` (no model call yet) or `EFFECT_STARTED` (the model call may have run). The CMO `agent_run` is still written once at the end by `_record_run` (unchanged); recovery uses the lease, the reservation (`request_key` stored on the lease) and the artefact rows. `CLAIMED` → release the reservation. `EFFECT_STARTED` with `COMPLETE` artefacts → adopt (settle reservation, usage by the existing per-artefact keys only if not already recorded); with none → `OUTCOME_UNKNOWN`, reservation released, nothing charged. **Open question D-L5:** whether CMO should also write a `RUNNING` row at acceptance (a change to its accounting path); the lease makes it unnecessary for recovery.

### 7.2 PI quota reservations and TTL expiry (audit G6)
Reservations expire silently at their TTL and the admission transaction counts only unexpired ones, so an expiry while a leg is alive can let a second request past a cap (audit L10). Two options (D-L4):
- **A (no schema):** the owner extends `expires_at` by the already-configured reservation TTL at each boundary (`UPDATE … WHERE state = 'RESERVED'`, fenced by the lease epoch). A live leg's reservation therefore never lapses; a dead leg's lapses at most one TTL after its last boundary, or is released earlier by recovery.
- **B (schema):** link `reservation.lease_id` and count a reservation as live while its lease is non-terminal, regardless of `expires_at`; expiry then becomes a pure backstop.
Recommend **A first**, because it uses no new number and no new column.

## 8. Billing and idempotency (requirement 6)
- Usage is written only (a) by the owner inside the fenced completion transaction, or (b) by recovery from a stored decision for an adopted leg; both use the existing unique `(tenant_id, idempotency_key)` keys, so any interleaving yields at most one event per key.
- A revoked or stale owner's usage write is rejected by the gate (§5.3 step 1), which closes the "stale worker bills after recovery" path.
- `OUTCOME_UNKNOWN` and `NOT_DISPATCHED` never produce an event. `unit_decision`/`CEO_UNIT_RULE_2` is unchanged: a turn with an unknown or failed required leg consumes no CEO unit.
- Recovery never redispatches: no code path from the reconciler to `dispatch`/`invoke` (test T7).
- **Decision D-L2b (billing of a late proof):** a completion proven *after* a revocation (the specialist row says COMPLETE) is billed once via adoption under its stored decision. The stricter alternative, "revoked means never billed", would waste legitimately delivered, usable work; it is the owner's choice.

## 11. Staged implementation plan (none started; each stage reviewable, scratch-DB first)

- **Stage A (no schema, behaviour-preserving):** guarded `finish_run`/`update_turn` helpers and tests of audit L7; the first half of T3.

- **Stage C (choke-point legs):** dispatcher claim, marker, fenced completion for CFO/CI/GST; the deadline policy (D-L3) for internal legs; T1, T2, T4, T5, F1.
- **Stage D (PI):** seam inventory and guards, usage behind the gate, reservation extension; T2b, T9, T10, F2.
- **Stage E (CMO):** claim before reservation, adoption rules; T1b for CMO.
- **Stage F (reconciler):** R5a/b CLI and lazy trigger on the lease; then R5c repairs from stored decisions; T3, T6, T7, T8, F4.
R5 stays **BLOCKED** until Stage F's tests pass **and** the owner accepts; approval must not be enabled before then (VP-2).

## 14. Technical decision review (code-validated, 2026-10-10). All recommendations are proposals; nothing is accepted.

#### 14.1a Correction to §5.3 (completion order)
Because V3 rules out a single transaction, the completion is a **fenced sequence in which each step is idempotent and the lease reaches its terminal state last**: (1) guarded `agent_run` terminal write, (2) idempotent finding, (3) usage events by the existing keys, (4) reservation settle, each opened with `fenced_scope(lease)`; (5) lease `→ SUCCEEDED`. A crash or revocation part-way leaves a **non-terminal** lease with some idempotent facts written; recovery completes the missing ones (adoption, §6.4), and a revoked owner's remaining writes are rejected by the fence. This is why adoption must also repair a lease that never reached its terminal state.

### 14.2 Billing and late-completion policy

Facts that constrain it: usage is idempotent per `(tenant_id, idempotency_key)`; a PI/CMO usable result is billed once by its own rule (Q-R2, Q-R3); the CEO unit is decided once at finalisation and treats an absent required leg as failed (`ceo/billing.py`); an in-flight external call cannot be recalled (V2); recovery must not redispatch, charge an uncertain outcome, or introduce refunds (owner decisions Q-R4, spec C9).

| Policy | Consequence |
|---|---|
| **P1 Revoke a metered/external leg at the turn deadline** | Does not stop the call in flight; stops only **later** calls. The result of the in-flight call may still be written by package code (unfenced), so you can end with a usable result, a lease saying `OUTCOME_UNKNOWN`, and no usage: unbilled usable work and a result the seller cannot rely on. It also changes behaviour (late results stop arriving). Benefit: caps further provider spend and seller-data egress after the deadline. |
| **P2 Allow late completion under the lease** (today's behaviour, now fenced) | The leg completes, writes its finding and its usage by existing keys; the turn's stored record still says the leg was missing at finalisation and the CEO unit stays NOT_DUE. Billing follows the specialist's durable result, exactly as a direct call would. The seller sees the late finding. Risk: a seller retry while the first run is alive (handled by the duplicate rule, D-L11). |
| **P3 Record a late success after revocation but do not charge it** | Introduces **free usable work**: it contradicts Q-R2/R3 and creates an unbilled path that depends on timing. It is a change to billing semantics and needs your explicit decision; **not recommended**. |
| **P4 Uncertain external outcome → `OUTCOME_UNKNOWN`** | Safe and consistent: no usage, no refund, no retry, surfaced to the seller and the operator. Applies only when there is **no durable completion evidence**. |

**Recommended consistent policy (proposal):**
1. **Billing follows durable completion and the stored decision, never the deadline or the lease state** (P2 + P4 together): a usable completed result is billed once by the existing keys, whether it finished before or after the deadline or was adopted by recovery; an outcome with no durable completion is never billed.
2. **Do not revoke at the turn deadline by default.** The deadline keeps meaning "stop waiting" (current behaviour). Revocation is used only for (a) a proven dead owner, (b) a lost lease, and (c) an explicit operator abort. This **replaces my earlier D-L3 recommendation**: the code review shows revocation cannot stop the call it is meant to stop, and it manufactures an uncertain state for work that usually completes.
3. A result that appears **after** a lease reached `OUTCOME_UNKNOWN` (a zombie in-flight call writing package-owned domain rows) is an **orphan**: never billed, reported to the operator. This is a narrow, conservative corner; it can leak a little free usage and never over-charges.
4. No new charge and no refund is introduced by any recovery path; recovery writes usage only from a stored decision through the existing key.
